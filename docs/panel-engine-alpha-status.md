# Panel engine alpha

Isolated development branch: development/panel-engine-alpha, based on beta fix eda79e0. Build output is dist/panel-engine-alpha/Majesty Mod Manager - Panel Engine Alpha. Alpha settings, selected installation, scan baseline, named profiles, remembered-mod projection and generated output use the MajestyModManagerPanelEngineAlpha namespace. Its optional native patches and launch use a separate MajestyHD.PanelEngineAlpha.exe beside the original game executable. Beta and staged Workshop output remain separate.

Implemented boundaries include the WE1 vocabulary parser and typed panel/callback/image/control references, preserved ordinary text and row identities, versioned explicit external_patches declarations, loaded SMNU/STRT detection, aggregation with dependent-mod attribution, and independent optional QoL rows. A native engine component with positive paired protocol evidence and no Manager definition is admitted as a Standard mod without fake metadata. Typed panel references participate in the ordinary preferred-resource composition path. Verified generated-source SF call detection excludes comments, strings and a script-supplied function implementation of that name. Compiled-only call inference remains unavailable: such a component can declare its dependency explicitly, or the tester can install Scripted Ground Actions manually. A bytecode definition index is never treated as call proof.

The dependency prompt retains selections and offers Open Quality of Life / Not now. Optional patches are installed only through a user action. Installed status verifies a versioned descriptor, exact build hook, bundled revision, payload identity and native API proof windows. Launch rechecks the actual alpha executable. In-game acceptance on Public, beta2 and GOG is a separate user-operated check; static/native fixtures do not establish that acceptance.

### Independent continuation, November9

The native evidence is now split into reproducible, bounded checks rather than
a single claim that an engine supports three versions:

- `verify_panel_engine_hooks.py` records the actual factory CALL, existing
  Manager entry/result guards, stock GPL registration CALL and following tail
  JMP on each fixture. It reuses the owning profile columns and preserves their
  different addresses. Hook placement does not admit an engine module.
- `verify_panel_engine_data_clients.py` verifies the complete127-byte narrow
  assignment and109-byte raw attribute client plus139-byte data-tree client.
  String allocation/copy/free requests agree with the existing native string
  constructor/destructor; imports are identified by DLL and name. Allocator,
  exceptional, VM and actor implementations remain opaque.
- `verify_panel_engine_vtables.py` identifies native Integer, base unit-list,
  StatsWindow and basic-building class tables by complete-object locator and
  matching RTTI hierarchy. It checks only the consumed target slots. It does
  not certify the SDK's blanket40-slot vtable copy or a full object size.
- `verify_panel_engine_constructors.py` binds complete normal UI constructor
  bodies to those exact class tables, retaining stock view/unit arguments and
  the StatsWindow delegation. This rejects the many unrelated constructors
  with identical instruction templates. Base/exception implementations and
  complete teardown/layout still require their own applicable evidence.
- `verify_panel_engine_navigation.py` follows the actual native Back=0x1f4d
  case. Public compares that value directly; beta/GOG reach it through another
  control-dispatch arm. All use the stock null opener target, own-unit panel
  lookup and close result. The neighboring list-unit activation arm writes
  UI+48; Back skips that write, so it was excluded from the Back contract.
- `verify_panel_engine_ui_callers.py` reuses the shipped list presenter's
  explicit text/name/image profiles, checking their complete normal bodies.
  The name formatter's actual stock cdecl argument frame is also checked on
  each fixture; it is not treated as a thiscall method by similarity.
- `verify_panel_engine_agent_clients.py` checks the existing43-byte stock
  agent-reference resolver on each fixture. It pins the null/deleted guard
  before the associated-unit request and derives the lookup/association API
  targets without following those implementations. The SDK's direct list
  lookup path lacks that guard; `PanelEngineAgentClient.h` supplies the literal
  stock guard for the forthcoming module adapter, with local provider-double
  coverage. It is not active in any deployed engine yet and does not establish
  full actor lifetime, registry or cleanup behavior.
- `runtime/PanelEngineOwnerProbe.inl` exposes the source engine's existing
  loaded-view and per-class wrapper ownership. It creates no second registry.
  A native fixture with all56 game providers redirected to local doubles
  exercises ordinary panels, BASE/CLASS, init, command, navigation, events and
  one stock destructor with preserved flags/return. The fixture is not native
  game ABI verification. Manager runtime activation of the probes is pending
  the verified versioned module and remaining native closure.

### Native components with optional-engine declarations

An engine-native component may supply explicit `external_patches` without
becoming a Manager Merge component. The alpha admits a positive engine
component as Standard when its matching definition has no Manager custom
buildings, runtime features or runtime capabilities. A damaged/mismatched
definition or real Manager recipe retains the normal Merge admission path.
The original Dataset, CAM, strings, XML and compiled target remain owned and
loaded by the native component. Standard can be selected alongside Merge mods
in a normal Prepare/Launch; Classic Launch is not required for that combination.
Only overlapping GPL/XML enter the existing scoped reconciliation. Sources
must reproduce their loaded target before they participate. This is not a
semantic-passthrough escape for a Merge input and does not relax the existing
scoped CAM/GPL Merge inventory guard.

### Cold-start QoL catalog correction

The first installer matrix warmed the Python import graph and exercised helpers
individually. It therefore missed the startup worker pool's first import of
`alpha_ui`. A cold read of the packaged code reproduced an ImportError for
`rewrite` from that partially initialized module. The controller caught the
escaping pool exception by dropping the catalog, producing zero cards and a
misleading unsupported-game label even though both executable images matched
the Public profile. The underlying game helpers had not been deleted.

Shared alpha helper imports now finish before the worker pool starts. An
individual helper exception becomes that helper's error card and preserves the
recognized branch and other cards. Game-version display also has an independent
executable check. The QoL interpretation cache revision is incremented.

`verify_alpha_cold_start.py` runs the actual alpha entry in fresh processes on
Public, beta2 and GOG disposable fixtures, with and without the combined native
alpha executable/private layouts. The packaged check runs the real frozen EXE
through its headless regression switch, not the archive-loader test adapter.
Each case executes the controller's cold scan and cached reopening path, creates
the real Qt QoL cards offscreen, requires every declared helper to remain
applicable, and checks that game inputs and output-profile absence are unchanged.
No Majesty process or foreground window is started. Both source and packaged
checks are mandatory in `Build-PanelEngineAlpha.ps1`, with receipts under
`local/panel-engine-alpha/cold-start`. Existing installer/restore checks remain.

This correction concerns Python initialization, error isolation, packaging and
UI state only; it adds no native-game mapping. Graph commit
`f2644580d33ad98703361cd8fc88c825068161ef`, node515/source citation above and
shared-map20261 were consulted for relevance; no new native evidence gap is
needed for the startup correction.
